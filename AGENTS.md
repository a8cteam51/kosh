# kosh — Claude Code Plugin for WordPress QA

kosh is a Claude Code plugin that runs functional, performance, accessibility, shop, and AEO (answer-engine optimization) tests against live WordPress sites using Playwright MCP browser automation.

## Commands

Installing and running kosh is in `docs/getting-started.md`; these are for changing it. Work from a clone and start Claude Code there with `claude --plugin-dir .`: for that session the clone replaces an installed kosh, and `.claude/settings.json` pre-approves the browser tools.

No build step — the scripts are plain `node` and `bash`. The root `package.json` has two dependencies: `ajv`, for report validation, and `axe-core`, which `__kosh.contrast()` runs. axe's version is pinned exactly, since a new one can change which text passes: a plugin version always installs the same axe, though provenance doesn't record it. The tests' `jsdom`, `eslint` and `globals` live in `tests/package.json`, not the root: Claude Code runs `npm ci` in an installed plugin's root, devDependencies included. `evals/` has its own `package.json` for promptfoo. Install with `npm ci`: `npm install` rewrites the committed lockfile, which blocks the next `git pull`, so it's only for adding a dependency.

```bash
npm ci                                                     # once after cloning, and after any pull
npm ci --prefix tests                                      # the same, for the tests' jsdom and eslint
node --test "tests/*.test.js"                              # every test; CI runs the same line
node scripts/generate-report.js tests/fixtures/performance-opus-5-5-2026-10-14.json --performance  # renderer only: validates, skips the stamp and the archive
node scripts/page-capture.js summary https://example.com/ [<page>…]  # the rows a performance report's pages[] would get now
node scripts/compare-runs.js kosh-reports/data/archive/<name>.json…  # one block of rows per archived performance run
node scripts/check-links.js 'https://example.com/' ['<url>'…]         # each off-site link's status and final origin, never its page or path
```

`.github/workflows/ci.yml` runs both installs and the tests on every PR and on pushes to `trunk`, with no API calls. The promptfoo evals stay manual because they cost money.

## How a report is produced

1. A skill drives the browser through Playwright MCP and writes `kosh-reports/data/qa-report-<type>.json`. Meanwhile `collectors/capture.js` records every page the browser loads (timings, LCP and CLS, console errors, failed requests, tagging `byModel` those the model's own `browser_evaluate` made, from Chrome's initiator stack) into `kosh-reports/data/capture-<session id>.jsonl`.
2. `scripts/run-qa-report.sh` then, for that skill's own output:
   - merges the capture (`scripts/page-capture.js merge`), setting `timestamp` to when the run's browser first loaded a page (the model's own value only if the capture has none and it's a date), and for performance rebuilds `pages[]` from it, replacing anything the model wrote, and refuses the run if its browser wasn't held to the site while it measured (the off-host wall, below);
   - stamps `provenance` (`scripts/stamp-provenance.js`): plugin version, skill and `collectors/` hashes, the Playwright MCP args, the model and effort from the session's transcript, and a seal;
   - renders (`scripts/generate-report.js`), which validates against the schema first (`scripts/validate-report.js`) and refuses a mismatch, naming each field;
   - archives the JSON and the capture in `kosh-reports/data/archive/` under the HTML's name, then deletes the source so the next run writes a new file.
3. Any other report is stamped without the session's facts, rendered and copied to the archive, but never deleted, and nothing is merged.

Things that catch contributors out:

- `hooks/guard-capture.js` refuses edits to `capture*.jsonl` files and anything naming this session's capture. For commands that can reach a `kosh-reports/` kosh has run in (one holding a capture: anywhere in the session's project, or a run folder or a path in its `kosh-reports/` named by absolute path), it also refuses `*.jsonl` globs and any `rm` or `mv` of `kosh-reports/`, `kosh-reports/data`, the archive, or a glob of their contents, so clearing them is done by hand.
- The merge keeps only the visits from the last browser that loaded the report's host, since a performance run starts with `browser_close`. A skill that closes the browser mid-run drops what it measured before.
- `kosh-reports/` is the project's, not kosh's: `$CLAUDE_PROJECT_DIR/kosh-reports`, which Claude Code sets for the capture and the hooks. Bash commands don't get it, so the scripts use the nearest `kosh-reports/data` at or above the cwd, looking no higher than the git root, else `kosh-reports/` in the cwd. The name is kosh's own so a project's `reports/` never gets client data mixed in. If `kosh-reports/.gitignore` is missing, the capture adds one (`*`) when it creates `data/`, and so does every successful render, even when Playwright made the folder first, since reports hold client URLs and console text. Schemas, skills and `plugin.json` still resolve from kosh's own folder. `KOSH_REPORTS_DIR` moves where the scripts and the capture look (the tests use it), not where the skills write.

## Playwright MCP (`plugin.json`)

`.claude-plugin/plugin.json` declares the server, and JSON can't hold comments, so its reasons live here. `tests/mcp-config.test.js` pins all of it. There's no `.mcp.json`: in a clone, a project one starts a second browser beside the plugin's.

- The version is pinned: `@latest` would make it an unrecorded input to every run, so a bump is its own PR. A bump must check that `browser_evaluate` still passes its code to ``eval(`(${expr})`)``, which is how `capture.js` recognizes the model's requests; if it doesn't, they quietly read as the site's. And that it still answers `{ result, isFunction }`, where the off-host wall reads the gate check's answer; if not, the wall never goes up and every performance run is refused. It must also check that the run-code tool's name still contains `browser_run_code`, and which tools take a `filename` or `paths`, since `hooks/guard-browser.js` relies on both.
- `--isolated` keeps the browser profile in memory, so no cache, cookies or logins carry over from an earlier session.
- `--no-webmcp` stops a tested page from registering tools the model could call.
- `hooks/guard-browser.js` sees every kosh browser call, because the model reads text from the pages it tests and a page can ask it to reach past the page. No check on a call can stop steering inside the tools kosh allows, like a page asking the model to navigate elsewhere or put data in a URL, and every other site the model opens is more text like that. So a skill never opens a page on another host: `scripts/check-links.js` prints each off-site link's status and where it ends up (the scheme and at most the last 40 characters of the host), never its page or path. It refuses `browser_run_code_unsafe` (no flag turns it off), which runs code in Playwright's Node process with the user's access to their machine; page-side work goes through `browser_evaluate`. It refuses a `filename` on any other tool, and a screenshot's outside `kosh-reports/screenshots/`: Playwright writes that file anywhere in the project without a permission prompt, `browser_evaluate` writes the page's return value as JSON, so a page could have it write a `.claude/settings.local.json` that allows every command, and a screenshot could overwrite a capture, which `guard-capture.js` doesn't see. And it refuses `paths`, which `browser_file_upload` and `browser_drop` use to hand the page files from the project. With `plugin.json`'s `approve_browser_tools` option on (a `userConfig` boolean, shown in `/config`), it also answers PermissionRequest, which runs only for a call Claude Code would otherwise ask about, or deny in a session that can't ask (a background agent, `claude -p`), approving any call it wouldn't refuse to a tool in `.claude/settings.json`'s allowlist, so the turn after a gate pause doesn't prompt. A deny rule still wins, since the tool isn't offered at all, but an ask rule doesn't: Claude Code runs PermissionRequest for that rule's dialog too, and nothing in the hook's input tells the two apart (live, 2.1.309, `-p`; interactive unchecked). That goes for an ask rule in managed settings too; `allowManagedHooksOnly` is how an organization keeps the hook from running. It never approves on PreToolUse, where an approval would cover calls Claude Code wasn't going to ask about. It trusts `mcp_server`'s `source` and `name` (Claude Code 2.1.274 or later), not the tool-name prefix, as the hooks docs advise, and a tool a Playwright bump adds isn't on the list, so it still asks. The option is off by default because it's kosh approving its own tools in every session where kosh is enabled: text from anything Claude reads could then steer the browser without the user being asked, including sending data out in a URL or through `fetch` in `browser_evaluate`, and no check on the call can tell. It also turns a background agent's or a `-p` run's refusals into approvals, since the hook's input doesn't say nobody can be asked, and with `--permission-prompt-tool` or the Agent SDK's `canUseTool` the hook usually answers before the host. In auto mode, a call the classifier allows never reaches it (live, 2.1.309); whether a call it blocks does is unchecked. Unset, it reaches the hook as nothing, not the manifest's default; saved on, as `"true"`.
- `--init-script` loads `collectors/kosh.js`, a frozen `window.__kosh` in every page; `--init-page` runs `collectors/capture.js` in Node for every tab. Both are `${CLAUDE_PLUGIN_ROOT}` paths: a relative one resolves against the folder Claude Code starts in, and Playwright won't start if the file isn't there. `capture.js` must never throw, since an init-page error breaks every browser tool, and an edit to it needs a server restart.
- `capture.js` loads axe-core (~580 KB) into a page only when the model's `browser_evaluate` code names `__kosh.contrast`, evaluating it over CDP just before that code, so a page's CSP doesn't refuse it (checked with `script-src 'self'`, Playwright MCP 0.0.82, 2026-10-30), and tagged `kosh-evaluate` like the model's code. If axe can't be read or loaded, that call is refused with the reason rather than run, so a page's own `axe` never stands in for kosh's. It never goes in the init script, which runs on every page performance times, and there's no page-callable loader. axe lives in the page's `window.axe`, so a page can replace it, which only lets the page misreport its own contrast. It runs with `iframes: false`, so text in iframes isn't checked.
- `capture.js` is also the checkout wall, because "never place an order" can't be left to the model while `browser_click` and `browser_evaluate` are pre-approved and a page can ask for the click. It fails a request WooCommerce would act on, read the way PHP and WooCommerce read it: a POST (or one whose last `_method`, else `X-HTTP-Method-Override`, says POST, which the REST API honours whatever the request's own method) to the Store API checkout or order-pay route by path, `rest_route` or batch; `?wc-ajax=checkout` after `sanitize_text_field`, which WooCommerce runs on it (tags out, whitespace trimmed, leftover `%XX` dropped); or a body with the classic checkout's or order-pay form's submit field (`woocommerce_checkout_place_order`, `woocommerce_pay`), which WooCommerce acts on at any URL. Query strings and form bodies are parsed like PHP 8: `+` is a space, the last value wins, and a field name's spaces, dots and unmatched `[` become `_`, so `woocommerce.checkout+place[order` counts. That's the line: a spelling PHP and WooCommerce wouldn't read as an order isn't one, and a new one they would is a parsing fix, not another pattern. Never a nonce name: `update_order_review` posts the whole form, nonce included, on every field change. A part of a body Chrome can't give (a stream, a file from disk) is left out and the rest is still read, so a stream or a file is refused on an order URL and decided by the readable parts elsewhere. The capture records each block as `net::ERR_BLOCKED_BY_CLIENT`. It uses its own CDP session with `Fetch.enable` for every navigation, fetch, XHR and beacon, not a Playwright route, because any route turns off the page's HTTP cache and sends every request through Node, which would skew every performance run (checked in Playwright 1.64: a cacheable script loaded three times with a route, once without). Images, scripts and styles aren't paused; a navigation or fetch costs about 1 ms more. A paused request must always get an answer, or the page hangs. It's a backstop for a mistaken click, a page asking for one and a casual request, not a boundary: code the model writes in `browser_evaluate` can do anything a page can, so a store whose gateway can take money is never safe to run unattended, and an unattended run belongs on staging or a gateway in sandbox mode. It also misses express-pay buttons (Apple Pay, Google Pay, PayPal), which need a wallet login an isolated browser doesn't have, a checkout inside a cross-origin iframe, a service worker's requests, and a popup that posts before its tab's wall is on (closing that needs CDP auto-attach with the new tab paused).
- `capture.js` is also the off-host wall, because another site's page is text nobody running kosh controls, and the model reads it. It goes up when the model's `browser_evaluate` of `__kosh.gate(…)` answers both fields `null`, read in the capture's `page.evaluate` wrapper so a page can't raise it, and holds that browser to the page's host (`www.` aside, port included) until `browser_close`, writing a `wall` row, but only if that's the host the gate check was asked about, read from the model's code in Node, so a page that patches `URL` can't aim it at itself. Not before: the gate check needs another host's redirects and the person's login. Behind it, the checkout wall's `Fetch` pause also refuses a main-frame document on another host, which Chrome pauses at every redirect hop, so a click, a form post, a page's own `location` change and a site link that redirects away are all caught before the page loads; and a request on another host that the model's code sent, by its initiator stack, kept across redirect hops and waited for (up to 500 ms) when the pause arrives first, since CDP doesn't promise the order. An off-host iframe passes only in a page on the site's host (not a `blob:`, `data:` or `about:` page the model could build) and only if the model's code didn't make it; the site's own requests to other hosts (analytics, payments) pass. Init-page waits for both walls before it returns, since MCP navigates a new tab (`browser_tabs` `new` with a URL) right after; a popup that opened on another host is closed as its tab starts, since it loads before that tab's wall is on. The merge copies the `wall` row into the archive and the host into `provenance.heldTo`, which the stamp seals, and refuses a fresh performance run without one, or with one that went up after more than the first page on the site past any gate pages (a login on another host doesn't count), so a skipped or late gate check fails the report; an archive from before the wall still re-renders. It doesn't cover Bash (`curl`, WebFetch), an off-host iframe's text in a snapshot, a WebSocket, whose handshake `Fetch` can't pause, an `EventSource`, which Chrome pauses (as XHR) but sends with no initiator stack, so the model's reads as the site's, or data leaving in an image or script URL, which are never paused; that's also how `__kosh.imageSize(url)` measures an image on a CDN host through it, returning only its size (checked in Chrome with Playwright 1.64, 2026-10-28).
- `--output-dir ${CLAUDE_PLUGIN_DATA}/playwright-mcp` keeps the files Playwright names itself (page snapshots, console logs) out of the user's project, where `git add` would pick up client pages. A file given a name, like a screenshot, still resolves against the project. That folder survives plugin updates and holds every project's page text, so `--output-max-size` has Playwright delete the oldest files past 20 MB.
- Every `browser_*` tool a skill names must be in `.claude/settings.json`'s allowlist as `mcp__plugin_kosh_playwright__<tool>`, or it prompts mid-run. Claude Code applies that file only in a clone, so each skill's `allowed-tools` repeats the list for marketplace installs, and `guard-browser.js` reads it in every install as the tools `approve_browser_tools` covers. Its grant lasts one turn, so the turn after a gate pause asks again unless `approve_browser_tools` is on. It also pre-approves the scripts the skill runs, each rule written the way the skill tells the model to run it with `${CLAUDE_PLUGIN_ROOT}` for `<kosh>`, since a Bash rule matches the command's text: the same command quoted or with `bash` in front asks. `run-qa-report.sh`'s rule is the skill's exact command, because the script copies whatever JSON it's given into the project's archive. Performance's `node …/page-capture.js summary *` and functional-design's `node …/check-links.js *` are wildcards, since their arguments are URLs; the first leaves out `merge`, which rewrites whatever file it's given. `approve_browser_tools` doesn't cover the scripts, so they ask after a gate pause either way. And it pre-approves the one file the skill writes, its own report, as `Edit(kosh-reports/data/qa-report-<type>.json)`: `Edit` rules cover the Write tool, a `Write(path)` rule is accepted but never matches, and the relative path resolves against the folder Claude Code started in, missing folders included (live, 2.1.312, `-p` default mode).

## How it works

Each test is a **skill** (`skills/`), invoked directly as `/kosh:<name>`. The skill parses the URL and environment type from user input, then carries the full testing procedure — what to check, how to check it, and how to report findings. Results follow the structure defined in a **schema** (`schemas/`) and are saved as JSON reports, which are then rendered to self-contained HTML reports via scripts in `scripts/`.

```
skills/          → detailed testing procedures (the actual prompts)
schemas/         → JSON schemas that define report structure
shared/          → canonical blocks every skill carries a verbatim copy of (never read at runtime)
collectors/      → code Playwright MCP loads: `kosh.js` into every page as `window.__kosh` (tested with jsdom), `capture.js` in Node for every tab, which also blocks placing an order (tested with a stub page)
scripts/         → report generation, validation, provenance, the page-capture merge, summary and archive, the run comparison, and the off-site link checker
hooks/           → the PreToolUse guards: page captures (`guard-capture.js`), and browser tools that reach past the page (`guard-browser.js`, which also answers PermissionRequest for `approve_browser_tools`)
evals/           → promptfoo regression checks for skill decision rules (evals/README.md)
tests/           → `node --test` checks for the scripts, the collectors, the capture and its guard, skill-embedded snippets, undefined names in the code and the snippets (ESLint's `no-undef`), shared-block copies, Claude Code-only constructs in skills, tracked JSON files, the Playwright MCP flags, allowlist and browser guard, the promptfoo eval wiring, skill ↔ schema drift, report validation and redacted real reports (`tests/fixtures/`)
docs/            → user-facing guides (getting-started.md)
.github/         → the CI workflow (runs tests/ on every PR)
.claude/         → project settings and Playwright tool permissions
.claude-plugin/  → plugin manifest (plugin.json), which declares the Playwright MCP server (see above), and the marketplace that lists it (marketplace.json)
```

### How skills and schemas relate

Each test type has a matching set of files:

| Test | Skill | Schema |
|---|---|---|
| Functional & design | `skills/functional-design/SKILL.md` | `schemas/qa-report-functional-schema.json` |
| Performance | `skills/performance/SKILL.md` | `schemas/qa-report-performance-schema.json` |
| Accessibility | `skills/a11y/SKILL.md` | `schemas/qa-report-accessibility-schema.json` |
| Shop (WooCommerce) | `skills/shop/SKILL.md` | `schemas/qa-report-shop-schema.json` |
| AEO / AI mode | `skills/aeo/SKILL.md` | `schemas/qa-report-aeo-schema.json` |

If you add a new test type, you need both: a skill and a schema. Do not add a matching command: skills and commands share one `/kosh:` namespace, so the entry would appear twice in the slash menu.

## Contributing

### Adding or editing a skill

A skill is a prompt the model reads once and follows for the whole run. `skills/performance/SKILL.md` is the template the other four move to as they're rewritten; until then they keep their older style. A rewritten skill:

- Follows this outline, in prose with the reason for each rule, because a model given the why handles the case the rule didn't name: the shared preamble; a two-sentence role saying what a finding is; the environment table; the shared gate check; the pages to cover and the floor, stated once; what to test, phase by phase, with what counts and what doesn't; the severity guide with its reasons and two or three "not a finding / a finding" lines; the report section. No `MANDATORY` blocks, `- ✅` rule lists, `- [ ]` checklists or closing reminders: the schema, which refuses a report that doesn't match, and the rendered tables are the gate.
- Leaves measuring to code. Numbers come from the collectors and the page capture, and the model reads them (the performance skill through `scripts/page-capture.js summary`) rather than transcribing them: a number the model copies is a number it can get wrong. The model's report holds its judgment: findings with a cause, `testMethodology`, and `explorationPass` for anything beyond the checks.
- Points at its schema as the contract and shows one labelled illustrative example, with placeholders where a copied value would do harm (the timestamp, the model ID). `tests/schema-drift.test.js` validates the example.
- Carries the blocks in `shared/` as verbatim copies, because skills can't include files and a skill folder must hold everything it runs: every skill carries the preamble, the gate check and the `provenance.model` line, and the skills in `CARRIERS` in `tests/shared-blocks.test.js` carry the others (the screenshot rule, performance only so far). Edit the `shared/` file and every copy together; the test fails otherwise.
- Write a path to kosh's own files (`scripts/`, `schemas/`, `collectors/`, a skill's references) as `<kosh>/…`. The shared preamble defines `<kosh>` as the folder two above the skill's, because a skill runs from the user's project, where `kosh-reports/` goes, not from kosh's folder. `tests/portability.test.js` fails on a bare one.
- Don't add Claude Code-only constructs (host tool names like `PushNotification`, `/kosh:` references, `mcp__` tool names, `CLAUDE_…` variables, `$ARGUMENTS`, "Claude prompt"): other hosts load skill text verbatim. `tests/portability.test.js` holds today's count per file, counting each `shared/` block once in `shared/` rather than in every copy; lower a count when a rewrite removes one, never raise it. The frontmatter's `allowed-tools` isn't counted: hosts read it as metadata, and `tests/mcp-config.test.js` pins it.
- Put page-side code in `collectors/kosh.js` and call it from the skill in one line (`() => __kosh.<name>(…)`), not as a multi-line `javascript` block. `tests/skill-snippets.test.js` holds today's count of multi-line blocks per file; lower it when a block moves out, never raise it. `tests/lint.test.js` fails on a name a snippet uses but never defines, which compiles and only breaks live, mid-run; its `UNDEFINED` holds today's count of known ones per file; lower it when one is fixed, never raise it.
- Test your changes by running the skill against a real site and reviewing the report. For `functional-design` and `performance`, also run the promptfoo evals — see `evals/README.md`. A run started in the clone also loads this file and your Claude Code memory for the clone's folder, which a user's run doesn't have, so it can't show whether a skill change changed what the model does. For that, start Claude Code in another folder with `claude --plugin-dir <path to the clone>`: a plugin's CLAUDE.md loads only when Claude Code starts in its folder.

### Adding or editing a schema

Schemas define the structure of the JSON reports. If you change what a skill collects, update the matching schema. The report generation scripts (`scripts/generate-report.js`) depend on this structure. Only a schema that declares `$schema` is validated (shop, aeo and performance today; functional and accessibility are still example documents), and it must compile in ajv strict mode.

In the performance schema, URLs kosh navigated to (`url`, `visitedPages`, `pages[].url`, a finding's `pages`) use its `webUrl` definition, http(s) only; shop and aeo adopt it when they're rewritten. URLs read off the site, like a failed request's, stay plain strings: a malformed one is something to report, and a schema that refused it would push the skill to "fix" the site's data in the JSON.

`tests/fixtures/` holds real reports that must keep passing their schema (`tests/fixtures.test.js`), so a schema edit that would refuse a real run fails CI. A fixture kept to show a refusal pins its exact errors in that test's `EXPECTED_ERRORS` instead, as the three performance runs from before `pages[]` do for their shape (and `performance-opus-5-run-1.json` for its invented `summary`); they stay to show old archives still render without validation and to give `compare-runs.js` both shapes. A `<name>.capture.jsonl` beside a fixture is its redacted capture, and the merge must rebuild the fixture's `pages[]` from it. The repo is public, so a fixture keeps only its shape: hostnames become example domains, identifying page slugs generic ones, the site name `Example Site`, and free text placeholder text. The test fails on any hostname, IP address or `localhost` but an example domain; it can't catch a name.

## Git workflow

- **Main branch:** `trunk`
- **Branch prefixes:** `feature/`, `fix/`, `update/`, `add/`, `remove/`
- **Commit style:** conventional commits — `feat:`, `fix:`, `docs:`, `test:`, `chore:`, etc.
- **Merge strategy:** squash merge preferred for feature branches
- **PR requirements:** clear title, description of what changed and why
- **Releases:** a marketplace install updates when `plugin.json`'s `version` changes, not on every commit, so a merged change reaches users with the next version bump
